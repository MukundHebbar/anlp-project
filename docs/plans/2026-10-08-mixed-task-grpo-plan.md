# Plan: one GRPO run on a 1/3 SOLVE + 1/3 JUDGE + 1/3 RECONSTRUCT mixture

Date: 2026-10-08. Status: **done**. Stopped by hand at step 80; step 75 evaluated (results in `docs/reports/2026-10-08-grpo-transfer-report.md` §7b).

## 1. Question

Does one model trained by Dr. GRPO on an equal mixture of the three tasks match the single-task arms on each task?
And does it avoid their negative transfer? The RECONSTRUCT arm loses 10.7 on SOLVE; the JUDGE arm loses 1.1.

The run gives one new row in the transfer matrix: "Mixed (1/3 each)".

## 2. Batch composition: balanced mixed batches (decision)

**Options:**
- **A.** Every batch holds equal numbers of all three tasks.
- **B.** Batches rotate SOLVE → JUDGE → RECONSTRUCT, one task per batch.

**Decision: A, balanced mixed batches.**

**Why:**
1. **It is the standard in multi-domain RLVR.**
   - GURU (Cheng et al., 2025; math, code, science, logic, simulation, tabular) and the multi-domain study of Li et al.
     (2025; math, code, puzzles; Qwen2.5-7B, GRPO) train mixed-domain RL.
   - A 2026 gradient-surgery study defines "Mixed RL" as mixing domains *within each batch*, so every update applies all
     domains' gradients at once.
2. **B is sequential RL at a one-step period.** Sequential multi-domain RL shows "mode interference": each domain's
   update partly undoes the others'. With B:
   - every update pulls the weights toward one task;
   - AdamW's moment estimates swing between three gradient distributions;
   - with overlapped rollouts, a JUDGE batch is generated by a policy just updated on SOLVE, so the policy gap per
     update is larger.
3. **A's known problem, gradient conflict, is mild for RL.** A 2026 analysis ("SFT Conflicts, RL Coexists") finds RL
   updates for different tasks close to orthogonal, unlike SFT.
4. **Our objective handles mixing cleanly.**
   - GRPO advantages are computed within each question's 8 answers, so tasks never share a baseline.
   - The Dr. GRPO loss is a sum over kept answers divided by a constant, so each task's weight per step is fixed by
     its share of the batch: equal by construction.
5. **Less noise.** Every step moves all three tasks, so their curves are smooth and comparable step by step.

**What A needs watched:** reward scales differ by task (SOLVE 0/1; JUDGE 0/0.5–1; RECONSTRUCT continuous 0–1). Without
÷ std, a task with more within-group spread gets larger advantages. The trainer will log mean |advantage| per task. We
only act if one task's is more than 3× another's for 10+ steps, and then only by rescaling per task (an amendment,
not a default).

## 3. Data

- **Pool:** each task's FINAL-v3 training questions, minus its 200-question dev slice. These are the same seeded orders
  the single-task arms used.
- **Size:** the first **1,134 questions per task**, so **3,402** in total, the same data budget as one single-task pass
  (3,400). The mixed model sees as many questions as any single-task arm could, a third of them per task.
- **Order:** interleaved S, J, R, S, J, R, … so **every batch of 30 holds exactly 10 + 10 + 10**. Built
  deterministically by `opd.mixed_prompts(n_per_task)` and saved as a manifest
  (`data/manifests/final-v3/grpo-mixed-1134.json`).
- **Option:** the full 3 × 3,400 = 10,200 is 340 steps, about 40 h on 2 GPUs. Only if you ask.

## 4. Recipe (as the working SOLVE recipe, except the lr and the batch)

| Setting | Value |
|---|---|
| Start | untrained `Qwen/Qwen3.5-2B` (post-trained, non-thinking), v2 prompts |
| Algorithm | Dr. GRPO: advantage = r − group mean; loss = token sum / 16,384; one update per batch; β 0 |
| Rewards | unchanged per task (`rewards.reward(task, …)`): SOLVE checker v3; JUDGE 0.5 verdict + 0.25 step + 0.25 Jev(E+M)/8; RECONSTRUCT Jev staged score − drafts penalty; gated or truncated → 0 |
| **lr** | **2e-5** (as you asked; tied with 1e-5 at step 8 in the SOLVE probe), 5-step warm-up, constant after |
| **Batch** | **30 questions × 8 answers** (10 per task; 30 instead of 32 so it divides by 3) |
| LoRA / optimizer | r 64, α 64, all projections; AdamW, grad clip 1.0 |
| Sampling | T 1.0, top-p 1.0, 16k cap for every task, overlapped rollouts |
| Length | one pass = **114 steps** (3,402 / 30); no early stopping, you can stop it any time |
| Checkpoints | every 8 steps; the latest with optimizer state; top 3 by a combined rolling reward (§5) |
| GPUs | 2 (vLLM + trainer); never more than 4 with evals |

## 5. What gets tracked

**Per step and per task:**
- reward;
- questions with a learning signal (out of 10);
- mean |advantage|;
- length and truncation.

The overall step time is logged too, and each rollout records its task.

**Main training metric, the combined rolling reward:**
- the mean over the three tasks of each task's 8-step rolling reward **minus that task's steps 1–8 average**;
- that is, the average improvement per task, so the task with the largest reward scale cannot dominate;
- the top 3 checkpoints by it are kept (`adapters/best-step<k>`).

**Stop signals I'll report** (you decide whether to stop):
- any task's truncation above 15%;
- repetition above 0.5;
- any task's rolling reward falling more than 0.05 below its best for 16 steps.

## 6. Code changes

1. **`opd.mixed_prompts(n_per_task)`:** builds the interleaved list. Each item carries `task`, plus the keys the
   rewards need.
2. **`opd_train.run_opd`** with `task="mixed"`:
   - reward rows loaded for all three tasks;
   - `rw.reward(item_task, …)` per rollout;
   - Jev enabled when any JUDGE or RECONSTRUCT is present;
   - per-task metrics in `metrics.jsonl`;
   - `task` written into `rollouts/step<k>.jsonl`;
   - the combined best-by-reward rule.

   Single-task runs behave exactly as before.
3. **`opd_run.py`:** `--task mixed`. The prompts come from the mixed manifest, and the cap applies to every task.
4. **`select_checkpoint_mixed.py`:** the dev composite (§7).
5. **`mixed_grpo_pipeline.sh`:** the same structure as the SOLVE runner (the fixed version), with three-task dev and
   test evals.
6. **Tests:**
   - the mixed manifest: exactly 10/10/10 per batch of 30, no dev or test questions, deterministic, and no question
     repeated within the pass;
   - per-task reward dispatch on recorded answers;
   - per-task metrics;
   - the combined best rule.

## 8. Running it end to end (one runner script)

1. **Training:** 114 steps, about **14 h** at ~7 min/step. JUDGE and RECONSTRUCT answers are shorter than SOLVE's, so
   the step should be faster than SOLVE-only. Chunks resume from the newest optimizer state.
2. **Candidates:** the top checkpoint by combined rolling reward, the best every-8 checkpoint by it, and the last step.
3. **Dev eval** of each candidate on all three dev slices (200 questions):
   - SOLVE with 4 samples (checker v3);
   - JUDGE with 1 sample (deterministic metrics);
   - RECONSTRUCT with 1 sample (Jev, as in the earlier dev selection).

   About 30 min per candidate on 2 GPUs.
4. **Selection:** the highest dev composite = mean over tasks of the dev Δ against the untrained model, in points:
   SOLVE accuracy, JUDGE Youden's J, RECONSTRUCT score. Ties go to the later step.
5. **Test:** all three test sets (SOLVE 4 samples; JUDGE and RECONSTRUCT 1), about 3 h on 2 GPUs.
6. **27B judging** of the JUDGE and RECONSTRUCT test answers, about 1–1.5 h; calibration locally.
7. **Report:** the "Mixed (1/3 each)" row in the transfer matrix, with the same metrics and CIs, written into the
   2026-10-08 report. Each mixed-model task score is compared with the matching single-task arm, paired against the
   untrained 2B:
   - mixed vs SOLVE arm on SOLVE;
   - mixed vs JUDGE arm on JUDGE;
   - mixed vs RECONSTRUCT arm on RECONSTRUCT.

   Plus per-task training curves and the advantage-scale check.

## 10. Risks

| Risk | Mitigation |
|---|---|
| One task dominates the gradient (reward scale) | per-task \|advantage\| logged; per-task rescaling only as a documented amendment |
| RECONSTRUCT hurts SOLVE, as in its single-task arm | the mixture keeps SOLVE in every batch; reported directly as the SOLVE cell |
| JUDGE peaks early and declines, as in its arm | combined best-by-reward checkpoints plus dev selection among candidates |
| lr 2e-5 too high for 114 steps | stop signals (§5); every-8 checkpoints allow choosing an earlier step |
| Jev outages | a failed call drops that answer from the step (existing behaviour); we stop if >5% of answers fail |
| Comparability | the single-task JUDGE and RECONSTRUCT arms used lr 5e-5 and 8 × 8; the mixed run matches the SOLVE arm's recipe except lr 2e-5. Stated in the report |
